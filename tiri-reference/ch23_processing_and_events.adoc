[[ch-processing-and-events]]
== Processing & Events
indexterm:[processing loop] indexterm:[events] Kōtuku is an event-driven framework.  Programs interact with the system by entering a processing loop that dispatches messages, fires timers, and monitors signals.  This chapter defines the `processing` interface, the event subsystem, and the available garbage collector controls.

All processing functions are accessed through the `processing` namespace.

[[sec-the-processing-loop]]
=== The Processing Loop
indexterm:[processing loop] A Tiri script that creates a GUI or performs asynchronous I/O must enter the processing loop to receive and dispatch messages.  The loop is entered by calling `processing.sleep()`.

==== processing.sleep()

[.api]`err = processing.sleep([Seconds])`

Enters the processing loop.  While sleeping, the runtime dispatches queued messages, fires timer callbacks, and processes platform events (window repaints, input, network I/O).  The `ERR` code indicates the reason for waking.

`Seconds` specifies the maximum time to sleep in seconds.  If omitted or negative, the call blocks indefinitely until a quit message is received or all monitored signals fire.  A value of `0` processes all outstanding messages and returns immediately.

[source,tiri]
----
-- Block until the user closes the window
processing.sleep()

-- Process outstanding messages without blocking
processing.sleep(0)

-- Sleep for up to 5 seconds, wake early on signal
processing.sleep(5)
----

The garbage collector runs a full collection cycle on entry to `processing.sleep()` before the runtime begins waiting for events.  Exceptions apply if `Seconds` is `0` or the garbage collector is disabled by the script.

[discrete]
==== Return Codes

[cols="1,3a",options="header"]
|===
|Code |Meaning

|`ERR_Okay`
|All monitored signals fired, or messages were processed successfully.

|`ERR_Terminate`
|A MSGID_QUIT message was received.  The script is expected to exit.

|`ERR_Timeout`
|The specified timeout elapsed before all signals fired.
|===

[discrete]
==== Application Pattern

A standard Tiri application creates its user interface, then enters the processing loop.  The loop returns when the user closes the main window:

[source,tiri]
----
import 'gui/window'

win = gui.window({
   title   = 'Hello',
   width   = 400,
   height  = 300,
   center  = true,
   quit    = true
})

win.show()
processing.sleep()
----

==== processing.halt()

[.api]`processing.halt(Seconds)`

Blocks the calling process for `Seconds` seconds while dispatching messages in the background.  Unlike `processing.sleep()`, the call cannot be woken early by a signal — it always runs for the full duration.

`Seconds` must be a non-negative number.  A value of `0` processes all outstanding messages and returns immediately.

The garbage collector runs a full collection cycle before sleeping, unless `Seconds` is `0` or the garbage collector has been disabled.

Raises an exception if `Seconds` is not a number, or if it is negative.

[source,tiri]
----
-- Block for exactly 3 seconds
processing.halt(3)

-- Process outstanding messages without blocking
processing.halt(0)
----

[[sec-processing-callbacks]]
[%breakable]
=== Processing Callbacks
[discrete]
==== processing.delayedCall()

[.api]`processing.delayedCall(Function)`

indexterm:[processing callbacks] Schedules `Function` to execute on the next message processing cycle inside `processing.sleep()`.  The function receives no arguments and its return value is discarded.

Use `processing.delayedCall()` when an operation must not execute immediately — for instance, freeing an object from within its own callback, or deferring work that depends on the current event cycle completing first.

Raises an exception if `Function` is not a function value.  The exception message describes the type mismatch.

[source,tiri]
----
processing.delayedCall(function()
   print('Executed on the next processing cycle.')
end)
----

The scheduled function executes exactly once.  To schedule recurring work, call `processing.delayedCall()` again from within the callback.

[[sec-callback-context]]
==== Callback Context

`processing.delayedCall()` captures the context that is current at the point of registration, and installs it as the current context each time the scheduled function runs.

[%unbreakable]
[source,tiri]
----
monitor = entity { name = 'monitor', ready = false }

function monitor.arm()
   processing.delayedCall(function()
      &ready = true       -- 'monitor', captured at registration
   end)
end
----

<<sec-context-and-callbacks>> defines the rules for every interface that captures a context.

[discrete]
==== processing.task()

[.api]`task = processing.task()`

Returns a Kōtuku Task object that represents the current process.  The returned object provides access to task-level properties such as process priority.  The object is detached: it references an external resource and is not owned by the script.

[source,tiri]
----
task = processing.task()
task.priority = 15
----

[[sec-signals]]
=== Signals
indexterm:[signals] Signals provide a lightweight synchronisation mechanism for waking a sleeping script.  A signal is a boolean flag on a Kōtuku object that transitions from _cleared_ to _raised_ when the object's `Signal` action is invoked.  There are no limitations on the class of object that can be used for signalling.

[discrete]
==== Default Signal Behaviour

When `processing.sleep()` is called without a custom processing object, it monitors the script object itself for a signal.  Any code — including callbacks and other threads — can wake the sleeping script by calling `processing.signal()`:

[source,tiri]
----
-- In a callback or event handler:
processing.signal()

-- The sleeping processing.sleep() call returns with ERR_Okay
----

[discrete]
==== Custom Signal Lists

For thread synchronisation or multi-object coordination, create a processing object with a list of objects to monitor.  The call to `sleep()` returns when the timeout elapses, or when the monitored objects satisfy the object's `mode`: every listed object signalled under the default `'all'`, or any one of them under `'any'`.

==== processing.new()

[.api]`proc = processing.new([Options])`

Creates a processing object.  `Options` is an optional table with the following fields:

[cols="1,1,5a",options="header"]
|===
|Field |Type |Description

|`timeout`
|number
|Maximum sleep duration in seconds.  Defaults to indefinite (`-1`).

|`signals`
|array<obj>
|An `array<obj>` of Kōtuku objects to monitor for signals.  If omitted or empty, the script object itself is monitored.

|`mode`
|string
|`'all'` requires every listed object to be signalled before `sleep()` returns.  `'any'` returns as soon as one listed object is signalled.  Defaults to `'all'`.
|===

Raises an exception if `signals` is not an `array<obj>`, if an entry in the array is `nil` or is not an available object, if `mode` is not the string `'all'` or `'any'`, or if an unrecognised option is provided.

[source,tiri]
----
objects = array<obj> { obj<Time> {}, obj<Time> {} }

proc = processing.new({
   timeout = 5,
   signals = objects
})

err = proc.sleep()
----

The processing object exposes the following methods:

[cols="2,5a",options="header"]
|===
|Method |Description

|`proc.sleep([Seconds])`
|Enters the processing loop with the configured signal list.  `Seconds` overrides the timeout set in `processing.new()`.

|`proc.signal()`
|Raises the signal on the script object.  This has no effect if the processing object was created with a custom `signals` list, because the script object is not in the monitored set.

|`proc.flush()`
|Clears the signal flag on the script object and on every object in the `signals` list.
|===

==== processing.signal()

[.api]`processing.signal()`

Raises the signal flag on the script object, waking any `processing.sleep()` call that is monitoring it.

==== processing.flush()

[.api]`processing.flush()`

Clears the signal flag on the script object.  Use this to reset signal state before entering a new `sleep()` cycle, particularly after a timeout where signals may remain pending.

[discrete]
==== Signalling from Threads

A common pattern uses signals to synchronise a worker thread with the main script.  The thread performs its work and then signals one or more objects to wake the main thread:

[source,tiri]
----
files = array<obj> { <1>
   obj<File> { ... }
}

script = obj<Tiri> {
   statement=[[ msg('Thread is now in session.') ]] <2>
}

script.setKey('Files', files.concat(',')) <2>

thread.script(script,
   function() <3>
      files.each(function(Object:obj)
         Object.acSignal()
      end)
   end)

proc = processing.new({ timeout = 10, signals = files })
choose proc.sleep() from
   ERR_Okay -> print('All signals received.')
   ERR_Timeout -> print('Timed out waiting for signals.')
   else -> print('Unexpected error.')
end
----
<1> Storing all objects that need to be processed in an array is a simple and effective processing pattern.
<2> Tiri threads are parsed separately to their parent block in order to maintain a safety barrier.  This prevents use of shared variables, but we can use `setKey()` and `obj.find()` to create safe references to the worker objects.
<3> The termination handler (the second argument to `thread.script()`) executes in the parent scope and can signal objects directly.

[[sec-the-event-subsystem]]
=== The Event Subsystem
indexterm:[events, subsystem] The event subsystem broadcasts system-wide notifications between all processes.  Events are identified by a hierarchical string in the format `group.subgroup.name`.  Tiri scripts can subscribe to events and receive callbacks when they are broadcast.

Events are dispatched during the processing loop (<<sec-the-processing-loop>>).  A script must be inside `processing.sleep()` to receive event callbacks.

[discrete]
==== subscribeEvent()

[.api]`err, handle = subscribeEvent(EventName, Callback)`

Subscribes to the event identified by `EventName`.  Returns an `ERR` code followed by a handle for later unsubscription.  If the subscription fails, `handle` is `nil`.

`EventName` is a string in the format `group.subgroup.name`.  All three parts are required.  The group is matched case-insensitively against the table below; the subgroup and name are case-sensitive.  A single-character wildcard `pass:[*]` is permitted in the subgroup and name positions to match all events within that level.

`Callback` must be a function value and receives two arguments: the numeric event identifier, and a table of event parameters.  The parameter table is empty for every event that the runtime broadcasts.  The callback observes the context that was current at the point of subscription (<<sec-callback-context>>).

[source,tiri]
----
err, handle = subscribeEvent('filesystem.volume.created', function(EventID, Args)
   print(f'Volume event received: {EventID}')
end)
----

[discrete]
===== Event Groups

[cols="1,3a",options="header"]
|===
|Group |Description

|`filesystem`
|File system changes (volume creation, deletion, file modifications).

|`network`
|Network state changes.

|`system`
|System-level events (task creation, shutdown).

|`gui`
|Graphical user interface events.

|`display`
|Display and monitor events.

|`io`
|Input/output device events.

|`hardware`
|Hardware state changes.

|`audio`
|Audio subsystem events.

|`user`
|User-defined application events.

|`power`
|Power management events (sleep, wake, battery).

|`class`
|Class registration events.

|`app`
|Application-level events.
|===

Raises an exception if the group name is not recognised, or if the event string does not supply all three parts.

[discrete]
===== Wildcard Subscriptions

Use `pass:[*]` in the subgroup or name position to receive a broader set of events:

[source,tiri]
----
-- Listen for all filesystem events
err, handle = subscribeEvent('filesystem.*.*', function(EventID)
   print('Filesystem event received.')
end)
----

[discrete]
==== unsubscribeEvent()

[.api]`unsubscribeEvent(Handle)`

Removes the event subscription identified by `Handle`.  The handle must have been returned by a prior call to `subscribeEvent()`.  After unsubscription, the runtime discards the callback and releases associated resources.

[source,tiri]
----
unsubscribeEvent(handle)
----

All event subscriptions are automatically cleaned up when the script terminates.

[[sec-timers-and-scheduling]]
=== Timers & Scheduling
indexterm:[timers] indexterm:[scheduling] Reliable timer subscriptions are available through the system core, `mSys`.  Timers fire callbacks at regular intervals during the processing loop.

[discrete]
==== mSys.SubscribeTimer()

[.api]`err, handle = mSys.SubscribeTimer(Interval, Callback)`

Creates a timer subscription that calls `Callback` at the specified `Interval` (in seconds).  Returns an error code and a handle for later modification or removal.

The `Callback` function receives three arguments:

[cols="1,1,3a",options="header"]
|===
|Parameter |Type |Description

|`Subscriber`
|object
|The subscribing object (your script).

|`Elapsed`
|integer
|Microseconds elapsed since the last call.

|`CurrentTime`
|integer
|The current `PreciseTime()` value at the moment the callback fires.
|===

The callback captures the current context at the point of subscription and observes it on every tick (<<sec-context-and-callbacks>>).  The captured table is released when the subscription is removed.

To cancel the subscription from within the callback, use `raise ERR_Terminate`.

[source,tiri]
----
-- Fire a callback roughly every 10 milliseconds
err, timerHandle = mSys.SubscribeTimer(0.01,
   function(Subscriber, Elapsed, CurrentTime)
      -- Perform periodic work
      print(f'Elapsed: {Elapsed} µs')
   end)
----

Timer callbacks are dispatched by the event processing loop in `processing.sleep()`.  Small intervals require frequent message processing to maintain reliable timing.

TIP: Timer intervals include the time spent in the callback.  With a one-second interval and a 400ms callback, the next execution cycle begins after 600ms.

[discrete]
==== mSys.UpdateTimer()

[.api]`err = mSys.UpdateTimer(Handle, Interval)`

Modifies an existing timer subscription.  `Handle` is the value returned by `mSys.SubscribeTimer()`.  Setting `Interval` to `0` removes the subscription entirely.

[source,tiri]
----
-- Change the timer interval to 0.5 seconds
mSys.UpdateTimer(timerHandle, 0.5)

-- Remove the timer subscription
mSys.UpdateTimer(timerHandle, 0)
----

[discrete]
==== Timer Patterns

[discrete]
===== Animation and Rendering

Timers are commonly used for animation loops.  The following pattern drives a particle simulation at high frequency:

[source,tiri]
----
function animate(Subscriber, Elapsed, CurrentTime)
   -- Update positions and redraw
   viewport.acDraw()
end

err, animTimer = mSys.SubscribeTimer(0.001, animate)

window.show()
processing.sleep()
----

[discrete]
===== Self-Cancelling Timers

A timer can cancel itself by calling `raise ERR_Terminate` from the callback.  The timer handles the exception without affecting the script:

[source,tiri]
----
err, handle = mSys.SubscribeTimer(1.0,
   function(Subscriber, Elapsed, CurrentTime)
      print('This fires once, then cancels.')
      raise ERR_Terminate
   end)
----

[discrete]
===== Adjusting Timer Intervals

Call `mSys.UpdateTimer()` to dynamically adjust the interval, for example to reset the elapsed counter after a delay phase:

[source,tiri]
----
err, handle = mSys.SubscribeTimer(1*fps,
   function(Subscriber, Elapsed, CurrentTime)
      if delayComplete then
         mSys.UpdateTimer(handle, 1*fps)  -- Reset the elapsed counter
      end
   end)
----

[discrete]
==== One-Shot Deferred Execution

Use `processing.delayedCall()` (<<sec-processing-callbacks>>) to schedule a function for execution on the next processing cycle.  This is the equivalent of a zero-delay timer.

[discrete]
==== Timeout-Based Coordination

For simple periodic work that does not require a dedicated callback, use a loop around `processing.halt()`:

[source,tiri]
----
while true do
   processing.halt(1)
   -- Perform periodic work every second
   print('Tick.')
end
----

Using `processing.halt()` ensures the loop runs for the full timeout on every iteration and cannot be interrupted by signals.

Combine `processing.new()` with a timeout to implement deadline-based waiting:

[source,tiri]
----
proc = processing.new({ timeout = 30, signals = array<obj> { download_obj } })
err = proc.sleep()

if err is ERR_Timeout then
   print('Download did not complete within 30 seconds.')
end
----

[[sec-garbage-collector-control]]
=== Garbage Collector Control
indexterm:[garbage collector] The `processing` namespace provides functions to control and query the Tiri garbage collector.  The collector runs automatically by default, reclaiming memory used by unreachable values.

[[sec-collector-design]]
==== Collector Design

indexterm:[garbage collector, design] The collector is an incremental mark-and-sweep tracer.  Liveness is decided by reachability: the collector traverses a root set that comprises the script's global table, its context stack, the active call stack, open upvalues and the internal registry, and reclaims every value that the traversal does not reach.  Reference counts are not maintained, so a group of values that reference one another is reclaimed as soon as the group as a whole becomes unreachable.

A collection cycle runs in three phases:

[cols="1,4a",options="header"]
|===
|Phase |Behaviour

|Mark
|Traverses reachable values from the root set.  Runs in increments that are interleaved with script execution.

|Atomic
|Completes the traversal, resolves weak tables and queues finalisers.  Runs to completion without interleaving.

|Sweep
|Reclaims unmarked values and invokes queued finalisers.  Runs in increments that are interleaved with script execution.
|===

Collection does not relocate values, and the cost of a cycle is proportional to the volume of live data, not to the volume of garbage.

Each script owns its heap and its collector.  A script executed with `thread.script()` (<<ch-threading>>) collects independently of its parent, and `processing.gcStats()` reports memory for the calling script alone.

The collector governs Tiri values — strings, tables, arrays, structs, closures and coroutines — and the interfaces that own Kōtuku resources.  Reclaiming an interface created with `obj<Class> { }` or `obj.new()` terminates the underlying object.  Interfaces obtained from `obj.find()`, created as children of another object, or demoted by `detach()`, hold weak references and are not terminated by collection (<<sec-object-lifecycle>>).  Reclaiming a table or full userdata that carries a `pass:[__]gc` metamethod invokes that finaliser once, immediately before the value is reclaimed (<<sec-garbage-collection>>).

[discrete]
===== Scheduling

Allocation drives the collector.  Each allocation compares total memory in use against a threshold and performs one incremental step when the threshold is reached.  Steps occur in interpreted and JIT-compiled code alike.  Two parameters, both reported by `processing.gcStats()`, define the schedule:

[cols="1,4a",options="header"]
|===
|Parameter |Effect

|`pause`
|The percentage of the previous cycle's live-memory estimate at which the next cycle begins.  The default of `200` starts a cycle when the heap reaches twice the estimated live size.

|`stepMul`
|The work performed by each incremental step, as a percentage of the base step size.  The default of `200` advances collection at twice the rate of allocation.
|===

Neither parameter is configurable from Tiri.

[discrete]
===== Behaviour in Practice

A script that builds an interface, performs its work in callbacks and returns to `processing.sleep()` requires no collector management.  The full cycle performed on entry to the processing loop (<<sec-automatic-collection>>) reclaims the garbage produced by the preceding burst of activity, so the resident heap stays close to the working set and cycles fall at points where the script is idle.

Two properties of the design have consequences for program structure:

* Reclamation is not immediate.  The interval between release of the last reference to a value and reclamation of that value is unbounded.  An object that holds a scarce resource — a file handle, a socket, a lock — retains that resource for the whole interval, so release it with `free()` or bind it to a `<close>` variable (<<sec-object-lifecycle>>).  Collection is not a release mechanism for scarce resources.
* A value that a live stack slot references is reachable.  A collection performed inside a function does not reclaim values that the function's own locals reference, irrespective of whether those locals are read again.

[discrete]
==== processing.collect()

[.api]`result = processing.collect([Mode], [Options])`

Triggers a garbage collection cycle.  Returns an integer whose meaning depends on `Mode`.

`Mode` is an optional string selecting the collection strategy:

[cols="1,3a",options="header"]
|===
|Mode |Description

|`'full'`
|Performs a complete collection cycle.  This is the default if `Mode` is omitted.

|`'step'`
|Performs an incremental collection step.  Returns `1` if the step completes a collection cycle, `0` if the cycle remains in progress.

|`'defer'`
|Records a request for a full collection cycle to run when the script next returns control to the runtime.  No collection takes place during the call.  Returns `0`.
|===

`Options` is an optional table with the following field:

[cols="1,1,3a",options="header"]
|===
|Field |Type |Description

|`stepSize`
|integer
|Work budget for the step, in kibibytes (only used with `'step'` mode).  Larger values complete cycles sooner and lengthen the pause caused by the call.  Values of 16 to 64 suit calls made from a frame or event loop; values of 100 and above suit idle-time collection.
|===

`Options` has no effect in `'full'` and `'defer'` modes.

Raises an exception if `Mode` is not a recognised string.

[source,tiri]
----
-- Full collection (default)
processing.collect()

-- Incremental step
result = processing.collect('step', { stepSize = 100 })

-- Request a collection for the end of the current callback
processing.collect('defer')
----

[[sec-deferred-collection]]
==== Deferred Collection

indexterm:[garbage collector, deferred collection] indexterm:[callback boundary] A request made with `processing.collect('defer')` is fulfilled at the next _callback boundary_, which is the point at which a Tiri callback returns control to the runtime.  The following are callback boundaries:

* Action and method subscription notifications (see <<ch-the-object-system>>).
* Event subscriptions (see <<sec-the-event-subsystem>>).
* Input and keyboard handlers (see <<ch-input-handling>>).
* Data feeds received by the script.
* Functions scheduled with `processing.delayedCall()`.

The runtime performs one full collection cycle at the boundary and clears the request.  Requests do not accumulate: any number of `processing.collect('defer')` calls made before a boundary produce a single collection cycle.

If the automatic collector is stopped, no collection takes place at the boundary and the request is retained.  The request is fulfilled at the first boundary reached after `processing.startCollector()` is called.

Deferring is the correct choice for a callback that releases the last reference to a group of values, because a collection performed inside the callback cannot reclaim values that the callback's own stack frame still references.  Once the frame is unwound at the boundary, those values are unreachable and are reclaimed by the deferred cycle:

[source,tiri]
----
surface.subscribe('free', function(UID, Args, CustomRef)
   table.clear(state)          -- Drops the last references held by the script
   processing.collect('defer') -- Reclaimed once the callback returns
end)
----

NOTE: The `'defer'` mode is unrelated to the `defer` statement, which runs a block on scope exit; see <<sec-defer-statement>>.

[[sec-automatic-collection]]
==== Automatic Collection

indexterm:[garbage collector, automatic collection] While the automatic collector is running, the runtime performs a full collection cycle at these points, and at no others:

* On completion of the first execution of the script's top-level code, which discards temporary values created during initialisation.  Subsequent executions do not collect.
* On entry to `processing.sleep()` and `processing.halt()`, unless `Seconds` is `0`.
* At the first callback boundary following a `processing.collect('defer')` request.

Returning from a callback does not otherwise trigger a collection cycle.  A script that allocates heavily within callbacks and does not enter the processing loop must request collection explicitly with `processing.collect()`.

NOTE: Incremental collection continues to run under the collector's own scheduling in all cases.  The points listed above define when a *full* cycle is guaranteed.

[[sec-manual-collection]]
==== Manual Collection

indexterm:[garbage collector, manual collection] Call `processing.collect()` when the timing of a cycle matters to the program.  The following cases warrant it:

* A callback drops the last references to a body of data and the script does not return to the processing loop afterwards.  Use the `'defer'` option so that the cycle runs once the callback's frame is unwound (<<sec-deferred-collection>>).
* A computation runs to completion without entering the processing loop.  A full cycle at each stage boundary returns the resident heap to the live set, where the automatic schedule allows it to reach twice that size.
* A latency-sensitive phase is about to begin, such as an animation sequence, a benchmark or a real-time render.  A full cycle immediately beforehand starts the phase with no accumulated garbage, so the phase allocates an amount equal to the live set before the collector resumes stepping.
* Memory is being measured.  `processing.gcStats()` reports the heap in use, which includes garbage that has not been reclaimed.  A full cycle before the measurement reduces the figure to the live set.
* Collection work is to be spread across chosen points rather than across allocations.  Call `'step'` mode from a timer or frame callback with a small `stepSize`.

Do not perform full collection inside a hot loop or on every frame.  The cost of a cycle is proportional to live data, so repeated full cycles over a large live set consume more time than the automatic schedule.

[discrete]
==== processing.stopCollector()

[.api]`processing.stopCollector()`

Stops the automatic garbage collector.  No automatic collection occurs until `processing.startCollector()` is called.  Manual collection via `processing.collect()` remains available.  The heap grows without bound while the collector is stopped, so restart it as soon as the phase that required stopping is complete.

[discrete]
==== processing.startCollector()

[.api]`processing.startCollector()`

Restarts the automatic garbage collector if it was previously stopped.

[discrete]
==== processing.gcStats()

[.api]`stats = processing.gcStats()`

Returns a table containing garbage collector statistics.

[cols="1,1,3a",options="header"]
|===
|Field |Type |Description

|`memoryKB`
|integer
|Memory usage in kilobytes.

|`memoryBytes`
|integer
|Remainder bytes.  Total bytes = `memoryKB` × 1024 + `memoryBytes`.

|`memoryMB`
|number
|Total memory usage in megabytes (convenience field).

|`isRunning`
|boolean
|`true` if the automatic collector is running.

|`pause`
|integer
|Current pause multiplier controlling collection frequency.  Default is `200`.

|`stepMul`
|integer
|Current step multiplier controlling collection speed.  Default is `200`.
|===

[source,tiri]
----
stats = processing.gcStats()
print(f'Memory: {stats.memoryMB} MB, GC running: {stats.isRunning}')
----

[discrete]
==== Memory Monitoring Example

[source,tiri]
----
before = processing.gcStats().memoryMB

t = {}
for i in {0 to 10000} do
   t[i] = string.rep('x', 100)
end

after = processing.gcStats().memoryMB
print(f'Allocated: {after - before} MB')

t = nil
processing.collect()
final = processing.gcStats().memoryMB
print(f'After collection: {final} MB')
----
